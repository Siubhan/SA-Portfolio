# Use Cases: Интернет-магазин

## UC-01: Оформление заказа

**Актёр:** Покупатель (авторизованный или гость)
**Предусловие:** В корзине есть хотя бы один товар
**Постусловие (успех):** Заказ создан, статус «Новый», покупатель получил подтверждение
**Триггер:** Покупатель нажимает на кнопку «Оформить заказ»

**Основной сценарий:**
1. Покупатель переходит в корзину и нажимает «Оформить заказ»
2. Система запрашивает контактные данные (или использует данные аккаунта)
3. Покупатель выбирает способ оплаты
4. Покупатель подтверждает заказ
5. Система создаёт заказ со статусом «Новый»
6. Система перенаправляет покупателя на страницу оплаты
7. Покупатель совершает оплату
8. Система подтверждает оплату и меняет статус заказа на «Оплачен»

**Альтернативные сценарии:**
- 2a. Покупатель не авторизован → предлагается авторизация, гостевой чекаут или регистрация
- 7a. Оплата не прошла → заказ остаётся в статусе «Ожидает оплаты», покупателю показывается ошибка с возможностью повторить попытку

**Исключения:**
- Товар закончился на складе между добавлением в корзину и оформлением заказа → система уведомляет покупателя и предлагает бронирование

**Связанные требования:** FR-08–FR-16

## UC-02: Регистрация аккаунта

**Актёр:** Пользователь (гость)
**Предусловие:** -
**Постусловие (успех):** Зарегистрирован новый пользователь
**Триггер:** Пользователь нажимает на кнопку «Зарегистрироваться»

**Основной сценарий:**
1. Пользователь на любой из страниц сайта магазина нажимает на кнопку «Зарегистрироваться»
2. Система запрашивает данные, необходимые для регистрации аккаунта
3. Пользователь вводит обязательные данные
4. Пользователь подтверждает регистрацию
5. Система оповещает об успешной регистрации аккаунта
6. Система перенаправляет пользователя на страницу личного кабинета

**Альтернативные сценарии:**
- 4a. Система обнаруживает, что аккаунт с указанными данными уже существует → предлагается восстановить пароль
- 4b. Введённые данные некорректны (например, неверный формат email, пароль не соответствует политике) → система указывает на ошибку и просит исправить данные

**Исключения:**
- У пользователя разорвалось соединение → регистрация в системе не была завершена

**Связанные требования:** FR-17

## UC-03: Восстановление пароля

**Актёр:** Пользователь (гость)
**Предусловие:** Пользователь испытывает трудности при входе в личный кабинет
**Постусловие (успех):** Пользователь успешно меняет пароль
**Триггер:** Пользователь нажимает на кнопку «Восстановление пароля»

**Основной сценарий:**
1. Пользователь нажимает на кнопку «Восстановление пароля» на странице авторизации
2. Система запрашивает данные, необходимые для восстановления доступа к аккаунту
3. Пользователь вводит данные, запрашиваемые системой
4. Система оповещает об отправке кода для восстановления доступа на указанные данные
5. Пользователь вводит код восстановления и меняет пароль
6. Система оповещает об успешной смене пароля
7. Система перенаправляет пользователя на страницу личного кабинета

**Альтернативные сценарии:**
- 3a. Покупатель вводит данные, по которым система не находит аккаунт → предлагается зарегистрироваться
- 4a. Код не приходит → предлагается повторная отправка спустя указанное время (delay)
- 4b. Код не приходит, но пользователь замечает, что указал ошибочные данные → пользователь возвращается для изменения введённых данных
- 5a. Введённый пароль не удовлетворяет политике защиты → система оповещает пользователя о необходимости коррекции пароля
- 5b. Пользователь вводит некорректный код восстановления → система оповещает пользователя о недействительном коде

**Исключения:**
- Отправка кодов временно недоступна

**Связанные требования:** FR-18

## UC-04: Бронирование товара при отсутствии на складе

**Актёр:** Покупатель (авторизованный)
**Предусловие:** Товар, интересующий покупателя, отсутствует в наличии
**Постусловие (успех):** Бронь зафиксирована, покупатель получит оповещение, когда товар появится в наличии
**Триггер:** Покупатель нажимает «Бронировать»

**Основной сценарий:**
1. Покупатель находит интересующий товар, отсутствующий на складе
2. Покупатель нажимает кнопку «Бронировать»
3. Система фиксирует бронирование, используя сведения об аккаунте покупателя
4. Система оповещает покупателя об успешном бронировании

**Альтернативные сценарии:**
- 2a. У покупателя истекла сессия / он не авторизован → система предлагает авторизоваться перед бронированием
- 4a. Срок брони истекает (например, через 3 дня) без оформления заказа → система автоматически снимает бронь и уведомляет покупателя

**Исключения:**
- Товар поступил на склад в ограниченном количестве, которого не хватает на всех забронировавших → бронь обрабатывается в порядке очереди (по времени бронирования), покупателям вне лимита приходит уведомление об отсутствии товара

**Связанные требования:** FR-10

## UC-05: Отмена заказа с возвратом оплаты

**Актёр:** Покупатель (авторизованный или гость, идентифицированный по заказу)
**Предусловие:** Заказ существует в статусе «Новый» или «Оплачен» (до отправки)
**Постусловие (успех):** Статус заказа — «Отменён»; если заказ был оплачен, инициирован возврат средств
**Триггер:** Покупатель нажимает «Отменить заказ»

**Основной сценарий:**
1. Покупатель открывает историю заказов (в личном кабинете или по ссылке из письма с подтверждением)
2. Покупатель выбирает нужный заказ и нажимает «Отменить заказ»
3. Система проверяет, разрешена ли отмена для текущего статуса заказа
4. Система запрашивает подтверждение отмены
5. Покупатель подтверждает отмену
6. Система меняет статус заказа на «Отменён»
7. Если заказ был оплачен, система инициирует возврат средств через платёжный шлюз
8. Система уведомляет покупателя об отмене и статусе возврата

**Альтернативные сценарии:**
- 3a. Заказ уже в статусе «Отправлен» или «Выполнен» → отмена через самостоятельный сценарий недоступна, система предлагает обратиться в поддержку
- 7a. Автоматический возврат средств невозможен (например, платёжный шлюз отклоняет операцию) → создаётся заявка на ручную обработку возврата администратором

**Исключения:**
- Платёжный шлюз временно недоступен при попытке возврата → заказ остаётся в статусе «Отменён, возврат в обработке», система повторяет попытку автоматически

**Связанные требования:** FR-15, FR-16

## UC-06: Обработка заказа администратором (смена статуса)

**Актёр:** Администратор
**Предусловие:** Администратор авторизован в админ-панели; заказ существует в системе
**Постусловие (успех):** Статус заказа обновлён, покупатель уведомлён об изменении
**Триггер:** Администратор открывает заказ и меняет его статус

**Основной сценарий:**
1. Администратор открывает список заказов в админ-панели
2. Администратор находит нужный заказ (поиск/фильтр по статусу, номеру, покупателю)
3. Администратор открывает карточку заказа
4. Администратор выбирает новый статус заказа (в обработке / отправлен / выполнен / отменён)
5. Система проверяет допустимость перехода между статусами
6. Система сохраняет новый статус и уведомляет покупателя (email / уведомление в личном кабинете)

**Альтернативные сценарии:**
- 5a. Выбранный переход статуса недопустим (например, из «Новый» сразу в «Выполнен», минуя отправку) → система показывает ошибку и не сохраняет изменение

**Исключения:**
- Уведомление покупателю не доставлено (ошибка отправки email) → статус заказа всё равно обновляется, ошибка логируется для повторной отправки уведомления

**Связанные требования:** FR-27

## UC-07: Управление товаром в каталоге администратором

**Актёр:** Администратор
**Предусловие:** Администратор авторизован в админ-панели
**Постусловие (успех):** Товар добавлен, изменён или удалён; изменения отражены в каталоге для покупателей
**Триггер:** Администратор выполняет действие с товаром в разделе «Товары»

**Основной сценарий:**
1. Администратор открывает раздел «Товары» в админ-панели
2. Администратор выбирает действие: добавить новый товар / отредактировать существующий / изменить остаток на складе
3. Администратор заполняет или изменяет данные товара (название, описание, цена, категория, фото, остаток)
4. Администратор сохраняет изменения
5. Система проверяет корректность введённых данных
6. Система сохраняет товар и обновляет каталог
7. Система подтверждает администратору успешное сохранение

**Альтернативные сценарии:**
- 2a. Администратор выбирает удаление товара → система запрашивает подтверждение → после подтверждения товар удаляется из каталога
- 5a. Введённые данные некорректны (например, отрицательная цена или пустое название) → система показывает ошибку, изменения не сохраняются

**Исключения:**
- Товар, который пытаются удалить, присутствует в незавершённых заказах → система блокирует физическое удаление и предлагает деактивацию (скрытие из каталога вместо удаления)

**Связанные требования:** FR-25, FR-26
