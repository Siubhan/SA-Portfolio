# ADR-004: Гостевой чекаут без обязательной регистрации

## Статус
Принято

## Контекст
FR-09 (Should-приоритет) требует возможности оформить заказ без регистрации аккаунта. Это решение, принятое на уровне требований, имеет прямые архитектурные последствия для схемы данных и авторизации, которые нужно зафиксировать отдельно от самого FR.

## Рассмотренные варианты

1. **Обязательная регистрация перед заказом**
   - Плюсы: каждый заказ гарантированно привязан к `Customer`; проще модель данных (`orders.customer_id` — обязательное поле, без доп. ограничений); вся история покупок автоматически доступна в личном кабинете
   - Минусы: дополнительный шаг перед покупкой повышает отказ от оформления заказа (общеизвестная проблема e-commerce — часть покупателей уходит, увидев форму регистрации); противоречит FR-09, который уже согласован

2. **Гостевой чекаут как опция наравне с оформлением через аккаунт**
   - Плюсы: ниже порог входа для разовой покупки; соответствует FR-09 и UC-01 (альтернативный сценарий 2a)
   - Минусы: усложняет модель данных — `orders.customer_id` должен допускать NULL; нужны отдельные поля для контактов гостя (`guest_name`, `guest_contact`); требуется constraint, гарантирующий, что хотя бы один из двух источников контактов заполнен; у гостя нет личного кабинета — отмена заказа и просмотр статуса должны работать по ссылке/номеру заказа, а не через авторизацию

## Решение
Выбран гостевой чекаут как опция. Реализовано на уровне схемы БД через nullable `orders.customer_id` и CHECK-constraint `chk_order_owner`, гарантирующий непротиворечивость данных (см. `06-data-model/schema.sql`):

```sql
CONSTRAINT chk_order_owner CHECK (
    customer_id IS NOT NULL OR (guest_name IS NOT NULL AND guest_contact IS NOT NULL)
)
```

## Последствия
- `Order.customer_id` — опциональная связь (0..1) с `Customer`, а не обязательная — это отражено в Class Diagram и ERD
- Отмена заказа гостем (FR-15/UC-05) не может полагаться на `bearerAuth` — в `openapi.yaml` эндпоинт `/orders/{orderId}/cancel` принимает и `guestSession`, альтернативный механизм идентификации нужно продумать отдельно (например, одноразовая ссылка из письма с подтверждением заказа)
- История покупок (FR-23) физически недоступна гостю после закрытия сессии — это ожидаемое ограничение, мотивирующее регистрацию постфактум, но не блокирующее саму покупку
- При конвертации гостя в зарегистрированного покупателя (если он решит зарегистрироваться после гостевой покупки) потребуется отдельная логика привязки прошлых гостевых заказов к новому аккаунту по совпадению контактов — это не покрыто текущими FR и является кандидатом в бэклог, а не для текущей версии
