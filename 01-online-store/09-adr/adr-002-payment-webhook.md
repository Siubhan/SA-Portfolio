# ADR-002: Webhook вместо polling для получения статуса оплаты

## Статус
Принято

## Контекст
После того как покупатель вводит данные карты на стороне платёжного шлюза, backend должен узнать результат оплаты (успех/отказ), чтобы обновить статус заказа и уведомить покупателя. Нужно решить, как backend получает эту информацию от внешней платёжной системы.

## Рассмотренные варианты

1. **Polling** — backend периодически опрашивает платёжный шлюз («платёж прошёл?») до получения финального статуса
   - Плюсы: не требует публичного эндпоинта, принимающего входящие запросы от шлюза; проще для локальной разработки (не нужен туннель вроде ngrok)
   - Минусы: задержка между реальным результатом оплаты и тем, когда система о нём узнает (зависит от интервала опроса); лишняя нагрузка — большинство запросов возвращают «ещё не завершено»; не масштабируется при росте числа одновременных заказов

2. **Webhook** — платёжный шлюз сам отправляет POST-запрос на эндпоинт backend, когда статус платежа меняется
   - Плюсы: уведомление приходит немедленно после обработки платежа; нет лишней нагрузки на опрос; стандартный подход для всех крупных платёжных провайдеров (ЮKassa, Stripe, CloudPayments)
   - Минусы: требует публично доступного HTTPS-эндпоинта; нужна проверка подлинности запроса (подпись от шлюза), иначе уязвимость к поддельным уведомлениям об оплате; сложнее тестировать локально

## Решение
Выбран **webhook**. Платёжный шлюз вызывает `POST /payments/webhook` после обработки платежа — это отражено в Sequence Diagram «Оплата заказа» и в `openapi.yaml`.

Причина: немедленное уведомление критично для пользовательского опыта (покупатель должен сразу увидеть подтверждение заказа, а не ждать следующего цикла опроса), а все реальные платёжные провайдеры, рассматриваемые для проекта, поддерживают webhook как основной механизм.

## Последствия
- Эндпоинт `/payments/webhook` должен быть доступен извне без авторизации покупателя — вместо этого нужна верификация подписи запроса от платёжного шлюза (HMAC или аналог, в зависимости от провайдера), иначе любой может подделать уведомление об успешной оплате
- Для локальной разработки потребуется инструмент туннелирования (ngrok, localtunnel), чтобы платёжный шлюз мог достучаться до локального backend
- Нужен fallback-сценарий на случай, если webhook не дошёл (сетевая ошибка, временная недоступность backend) — например, ручная сверка статусов администратором или редкий контрольный polling раз в несколько часов для «зависших» заказов в статусе `awaiting_payment`
