# ADR-003: UUID вместо auto-increment ID в качестве первичного ключа

## Статус
Принято

## Контекст
При проектировании схемы БД (`06-data-model/schema.sql`) нужно было выбрать тип первичного ключа для всех таблиц. Решение принято без отдельного обсуждения в процессе работы над ERD — фиксирую его здесь задним числом, чтобы оно не осталось необоснованным.

## Рассмотренные варианты

1. **Auto-increment integer (`SERIAL`/`BIGSERIAL`)**
   - Плюсы: компактнее по размеру (4–8 байт против 16 у UUID), быстрее при JOIN на больших объёмах, последовательные ID проще читать и отлаживать вручную
   - Минусы: ID предсказуем и раскрывает информацию (например, по ID заказа можно оценить общее количество заказов в системе — нежелательно для `/orders/{orderId}` в публичном API); при распределённой генерации (несколько серверов пишут одновременно) возможны коллизии без координации через БД

2. **UUID**
   - Плюсы: непредсказуем — нельзя подсмотреть примерный объём данных по ID в URL; можно генерировать на стороне приложения ещё до записи в БД (полезно, например, для `Reservation.id` при создании брони до подтверждения транзакции); не раскрывает порядок создания записей
   - Минусы: больше занимает места на диск и в индексах; чуть медленнее JOIN на очень больших таблицах; неудобно для ручной отладки через SQL-консоль (сложнее запомнить/напечатать)

## Решение
Выбран **UUID** для всех первичных ключей.

Причина: часть ID используется напрямую в публичных URL (`/orders/{orderId}`, `/products/{productId}`) — предсказуемый auto-increment ID позволил бы конкурентам или любопытным посетителям примерно оценить обороты магазина простым перебором (`/orders/1`, `/orders/2`...). Для нишевого бренда, который заботится о конфиденциальности бизнес-показателей (см. Vision, раздел про стейкхолдеров/инвесторов), это неприемлемо. Производительность на объёмах pet-проекта / малого бизнеса не является узким местом, которое оправдывало бы компромисс с предсказуемостью ID.

## Последствия
- Все FK-колонки в `schema.sql` имеют тип `UUID`, генерация через `gen_random_uuid()` (расширение `pgcrypto`)
- Индексы по UUID-колонкам занимают больше места, чем по integer — при росте БД стоит следить за размером индексов на `orders`, `order_items` как на самых объёмных таблицах
- Ручная отладка через `psql` менее удобна (длинные нечитаемые ID) — компенсируется использованием админ-панели и логов с человекочитаемым контекстом (email покупателя, номер заказа для отображения можно сделать отдельным коротким полем, если понадобится для клиентской поддержки)
