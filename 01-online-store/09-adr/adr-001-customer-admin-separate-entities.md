# ADR-001: Customer и Admin как раздельные сущности

## Статус
Принято

## Контекст
Системе нужно поддерживать два разных типа пользователей: покупателей (Customer) и администраторов (Admin). Нужно решить, моделировать ли их как одну сущность `User` с полем `role`, либо как две независимые сущности со своими таблицами и жизненным циклом.

## Рассмотренные варианты

1. **Единая сущность `User` с полем `role`**
   - Плюсы: одна таблица авторизации, проще логин/сессии/JWT, легко добавить новую роль без миграции схемы
   - Минусы: неизбежны поля, нужные не всем ролям (NULL-колонки — например, `phone`, корзина, избранное не нужны администратору); усложняется логика доступа («если role = customer, то...») разбросанная по коду

2. **Раздельные сущности `Customer` и `Admin`**
   - Плюсы: чистая модель без пустых полей; явно видно разное поведение и жизненный цикл каждой роли; нет риска случайно выдать покупателю админские права через баг в проверке роли
   - Минусы: дублирование инфраструктуры логина (два flow регистрации/авторизации); если в будущем понадобится роль, пересекающая обе (например, покупатель-амбассадор с частичным доступом к админке), потребуется рефакторинг

## Решение
Выбран вариант с раздельными сущностями `Customer` и `Admin`.

Причина: в рамках проекта роли **не пересекаются и не меняются** — покупатель никогда не становится администратором и наоборот (это не предусмотрено ни одним FR). При этом у `Customer` значительно больше полей и связанного поведения (корзина, избранное, брони, история покупок), специфичного только ему. В такой ситуации раздельные сущности дают более чистую модель данных без искусственных ограничений (NULL-полей, условной логики по роли).

## Последствия
- Авторизация реализуется как два независимых flow (`/auth/*` для покупателей, отдельная аутентификация для админки) — см. `openapi.yaml`
- В ERD/SQL это две отдельные таблицы (`customers`, `admins`) без общего родителя
- Если в будущем появится роль, пересекающая покупателя и администратора (менеджер поддержки с ограниченным доступом к заказам, например), потребуется либо завести третью сущность, либо пересмотреть это решение в сторону role-based подхода
